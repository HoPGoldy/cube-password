# 评审发现但不修复的问题（Not-Fix 清单）

> 背景：2026-09 对 cube-password 做了一轮全面安全评审（4 个模块并行评审 + 主线复核），
> 产出了若干 Should-fix 与低危发现。本文档记录**经讨论后明确决定不修复**的项及其理由，
> 避免未来的评审/agent 重复报告或误判。
>
> 阅读前请先看 [AGENTS.md](../AGENTS.md) 的 Principle——本项目的威胁模型是：
> nginx 反代路径是第一道防线；安全设计以「最快速暴露异常」为目标，
> **不抵抗已知服务地址的攻击者**（发现被攻击 → 换反代路径即可）。

## S1 · 挑战码单槽位覆盖 → 远程全天锁定（评审定级：中）

**现象**：`/auth/challenge` 无鉴权无限流，挑战码单槽位"生成即覆盖"。攻击者持续刷码，
受害者登录时携带的旧码已被覆盖，hash 比对失败并计入 3 次/天锁定 → 远程确定性 DoS。

**不修理由**：攻击者能刷 challenge 的前提是**已发现服务地址**——按设计哲学，地址泄露
本身就该触发锁定告警。覆盖攻击导致的登录失败 → 计数 → 全天锁 → 用户看到"密码错误"
通知 → 知道地址泄露 → 换 nginx 路径，链条完全闭合。花成本抵抗一个已知地址的攻击者，
与「快速暴露异常」的目标相悖。

曾考虑的方案（多槽位挑战码、接口限流）均已否决。

## S2 · totpSecret 明文落库（评审定级：中）

**现象**：全库凭证走 E2EE，但 `User.totpSecret` 明文存 SQLite。

**不修理由**：这里不是 Bitwarden——totpSecret 是**本系统自用**的验证因子（改密码确认、
分组 Totp 锁），不存任何外部服务的 2FA 种子。逐一核对所有校验路径后确认，拖库者拿到
明文 totpSecret **不构成独立的攻击能力**：

1. 登录：不校验 TOTP（只校验 hash 派生的 V）；
2. 改密码：需 session + 旧密码证明（`SHA512(V + challenge)`），TOTP 只是第三道门；
3. 分组 Totp 锁：需有效 session。

单独拿到 secret 既解不开凭证（E2EE），也过不了任何一条完整的验证链。

加密方案（key 文件 / 环境变量）同样被否决：攻击者若能脱库，同样能读 `storage/totp.key`
或 `/proc/1/environ` 里的 `TOTP_KEY`——加密只防"db 文件单独泄露"这个极窄场景，而该
场景下被保护的东西本无独立价值。

## S3/S4 · change-password / 分组锁解锁无失败计数，可无限爆破（评审定级：中）

**现象**：login 有 3 次/天全局锁，但 change-password 旧密码校验、分组 Password 锁、
分组 Totp 锁（6 位码空间 10⁶）三个入口失败不计数，持有 session 者可无限尝试。

**不修理由**：这三个入口的攻击前提都是「session 已被劫持」，而能劫持 session 的途径
（XSS、恶意插件、本机恶意软件）在同一时刻就能直接窃取内存中的 DEK 与屏幕明文——
给这三扇门加失败计数属「前门上锁、窗户开着」，是补丁而非根源修复。根源层面的对策
见优化方案：CSP、死依赖清理、绝对会话超时（10 分钟强制重登）。

## `/auth/global` 未认证下发 salt + kdfParams（评审定级：中，固有取舍）

**现象**：任何人可拉取 salt + kdfParams 后离线字典爆破，绕过在线 3 次/天锁定。

**不修理由**：salt/kdfParams 是 E2EE 登录协议的必要输入（客户端派生前必须拿到），无法
藏在认证之后。离线爆破的唯一载体是 argon2id（m=64MiB, t=2, p=1，约 0.5s/次），这与
Bitwarden 等同类产品的取舍一致。真正的防线是主密码强度（zxcvbn 已在 init/改密时警告）
与 nginx 隐藏。可选缓解：部署者在反代层对 `/api/auth/*` 限流（见 README 部署建议，不
改代码）。

## deleteGroup 无需解锁即可级联删除整组凭证（评审定级：中，计划内边界）

**现象**：`deleteGroup` 不校验分组是否已解锁，删除即级联清空该组全部凭证密文；
且删除后 `defaultGroupId` 可能悬挂。

**不修理由**：单用户单 session 模型下，能调用该接口的只有用户本人；前端删除确认需
输入分组名。锁定的组"不能移动一张凭证，却能整组删掉"确属哲学不一致，但这是有意保留
的逃生通道——**忘了锁密码的组还能靠删除来止损**。若强制"解锁才能删"，忘记密码的组
将永远无法清理。defaultGroupId 悬挂问题影响极小（前端导航容错）。

若后续重审此决策，方向应是"删除锁定组需输入锁密码"而非"禁止删除"。

## 评审中的其他"低危/信息"项处理结论

| 项 | 结论 |
| --- | --- |
| hash 比较未用 `timingSafeEqual` | 不修：被比较值是绑定一次性随机 challenge 的摘要，时序泄露无法累积，实际不可利用 |
| `/auth/init` TOCTOU 竞态（并发双用户） | 不修：窗口极窄（仅未初始化实例的首秒），单用户自部署场景无并发初始化的现实路径 |
| TOTP bind 无密码复核 | 不修：bind 需有效 session，session 劫持者本可直接读凭证明文，加复核不改变威胁面 |
| `parseKdfParams` 无参数上界 | 不修：下发参数的是自己的后端；后端被攻陷时攻击者可直接投喂恶意 JS，限制 KDF 参数无增量意义 |
| 凭证 URL 字段 `includes("http://")` 判定可被 `javascript:` 绕过 | 不修：需恶意内容先进入本机密码库（导入他人库/被诱导粘贴），单用户场景触发面极小；React + 无 dangerouslySetInnerHTML 已兜底主要 XSS 面 |
| e2e 默认密码 `admin` + 固定盐 | 不修（测试环境）：仅作用于 localhost 后端；已有探测逻辑不会改写已初始化的库 |
| init 成功后 `window.location.href = "/login"` 硬编码 | 不修：子路径部署本就是边缘场景（见 S6 修复时的关联说明） |
| SQLite 未开 WAL | 不修：单进程单连接 + 低写入量，无并发读写诉求 |
| `request.ip` 反代下归因失真 | 不修：仅用于通知文案的诊断信息；正确配置 trustProxy 属部署者责任，写文档反而诱导错误配置 |
| LICENSE 与 package.json 标注不一致 | 待用户拍板（GPL v3 vs MIT/ISC），非安全问题 |

> 注：上表"不修"均为**当前威胁模型下的接受**，而非永久承诺。若未来威胁模型变化
> （如开放多用户、公开部署），应重新评估本清单。
